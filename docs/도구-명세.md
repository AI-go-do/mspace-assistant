# MCP 도구 명세

> 기준: 요구사항 명세 v0.4, mspace-core 코드(`feat/7-room-availability`, PR #24 예약 생성, 11/2 확인). core에 아직 없는 API는 **확인 필요**로 표시해요.
> 도구가 core를 부르는 방식은 모두 같아요: 에이전트가 보낸 사용자 헤더(`Authorization`. 로그인 전 임시 `X-User-Id`는 `local` 프로필에서만)를 그대로 넘겨요. 관리자 토큰은 쓰지 않아요.
> `X-User-Id`는 core를 `MSPACE_DEV_HEADER=true`로 띄웠을 때만 켜져요. 진짜 core에 붙여 볼 때 꼭 켜요.

## 0. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 시각 | 입력·출력 모두 서울 시간 ISO-8601 `+09:00`. core 응답도 서울 시간으로 되돌려서 넘겨요 ([TS-01](트러블슈팅.md)) |
| 모델에 안 보내는 값 | 6자리 입실 번호(`accessCode`), 참여자 이름, 학번, 전화번호, 토큰 |
| 오류 | 도구 오류 결과(`isError: true`)에 core의 `message`를 그대로 담아요. 모델은 이 문장을 학생에게 전해요 |
| core가 꺼짐·3초 넘게 응답 없음 | `CORE_UNAVAILABLE` "예약 서버에 연결하지 못했어요. 잠시 후 다시 시도해 주세요." |
| 쓰기 도구 | 바로 실행하지 않고 확인안 + 확인 토큰을 돌려줘요 ([설계.md](설계.md) 2장) |

## 2. 읽기 도구

### 2.1 `find_available_rooms` (구현 완료, #6)

**언제:** "내일 오후 2시 빈방", "수업 끝나고 2시간 잡을 방" 같은 빈 시간 질문.

**입력**
```json
{ "date": "2026-11-03", "from": "14:00", "to": "16:00", "headcount": 4 }
```
- `date` 필수. `from`·`to`·`headcount`는 고르기용이라 없어도 돼요.

**core 응답** (`GET /api/rooms/availability?date=2026-11-03`)
```json
{ "date": "2026-11-03", "slotMinutes": 30,
  "rooms": [ { "roomId": 1, "roomName": "1번 방", "minPeople": 3, "maxPeople": 5,
               "slots": [ { "startAt": "2026-11-03T00:00:00+09:00", "endAt": "2026-11-03T00:30:00+09:00", "available": false }, "… 48칸" ] } ] }
```

**도구 출력** (48칸을 그대로 주지 않고 **이어진 빈 구간**으로 합쳐요. 방 5개 × 48칸 = 240줄이 모델 토큰을 먹고, 모델이 칸을 잇다가 틀리기 쉬워서예요)
```json
{ "date": "2026-11-03",
  "rooms": [ { "roomId": 1, "roomName": "1번 방", "minPeople": 3, "maxPeople": 5,
               "free": [ { "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T17:30:00+09:00" } ] } ],
  "note": null }
```
- `headcount`가 있으면 `minPeople ≤ headcount ≤ maxPeople`인 방만 남겨요.
- `from`·`to`를 둘 다 주면 그 시간 **전체**가 빈 구간 안에 들어가는 방만 남겨요. 빈 구간 목록은 그 방의 하루 전체를 그대로 줘요(모델이 다른 시간을 제안할 수 있게).
- `from`만 주면 그 시각 뒤에 끝나는 구간만, `to`만 주면 그 시각 전에 시작하는 구간만 남겨요.
- 맞는 방이 없으면 `rooms: []`와 `note: "조건에 맞는 빈방이 없어요. 다른 시간이나 날짜를 찾아볼 수 있어요."`
- `headcount` 때문에 방이 하나도 안 남으면 `note`가 달라요: `"2명이 쓸 수 있는 방이 없어요. 1번 방 3~5명, …, 5번 방 5~8명. 함께 쓸 사람을 더 넣어야 해요."` (가장 큰 방보다 많으면 "인원을 줄이거나 두 방으로 나눠야 해요") 빈 시간 문제와 인원 문제를 모델이 섞어 말하지 않게 이유를 적어요 (11/5 시연에서 2명 → "빈방 없음"으로 잘못 안내됨)
- `available: false`는 "지난 칸"이거나 "예약된 칸"이에요. 둘을 구분하지 않아요.
- **가까운 대안 `alternatives` (11/6):** `from`·`to`를 둘 다 줬는데 맞는 방이 없으면, 같은 날 **같은 길이**로 원하는 시작에 가장 가까운 시간을 최대 3개 줘요. 가까운 순 → 이른 시각 → 방 번호, 같은 시작은 한 번만. 지금보다 이른 시작은 빼요. `note`는 `"그 시간에는 빈방이 없어요. 같은 길이로 가장 가까운 시간은 alternatives에 있어요. …"`
  ```json
  { "date": "2026-11-03", "rooms": [],
    "alternatives": [ { "roomId": 2, "roomName": "2번 방", "startAt": "2026-11-03T15:00:00+09:00", "endAt": "2026-11-03T17:00:00+09:00" },
                      { "roomId": 1, "roomName": "1번 방", "startAt": "2026-11-03T11:00:00+09:00", "endAt": "2026-11-03T13:00:00+09:00" } ],
    "note": "그 시간에는 빈방이 없어요. …" }
  ```
  - 왜 서버가 고르나: 모델이 `free` 구간을 보고 "1시간 뒤엔 돼요"를 계산하다 길이·칸을 틀리기 쉬워서예요. 시연 장면 "2시 꽉 찼어요 → 3시 2번 방 어때요?"를 한 번에 맞게 해요.
  - 인원 때문에 비었거나 자정을 넘기는 시간이면 대안을 안 줘요(인원 안내가 먼저, 자정 넘김은 다음 날 칸을 몰라서). 방이 있을 때, `from`·`to` 중 하나라도 없을 때, 같은 길이가 들어가는 시간이 그날 하나도 없을 때도 `alternatives: []`예요

**자정 넘김 (11/2 지영님과 합의):** core는 그대로 두고, 비서는 **시작 날짜만 조회**해요.
- 예: 오늘 11/3, "11/9 23:00–11/10 01:00" → `date=2026-11-09`의 23:00·23:30 칸만 확인하고 바로 예약 확인안으로 가요.
- 11/10 칸은 조회 범위(오늘~+6일) 밖이라 `400 ROOM_DATE_OUT_OF_RANGE`예요. 예약 규칙은 **시작 시각만** 7일 안을 보니까 예약 자체는 돼요(core 테스트로 확인).
- 그래서 `note`에 "자정 이후 부분은 예약할 때 확인돼요"를 넣고, 확인안에도 같은 문장을 넣어요. 이미 차 있으면 예약 때 `409 RESERVATION_TIME_TAKEN`이 와요.

**오류**
- `400 ROOM_DATE_OUT_OF_RANGE` "오늘부터 예약 가능한 기간 안의 날짜만 조회할 수 있습니다"
- `400 INVALID_REQUEST` "요청 형식이 올바르지 않습니다" (`date` 형식이 틀리거나 없음. 비서가 날짜를 만들어 보내니 거의 안 나와요)

**이 도구의 한계:** 지금이 14:17이면 14:00 칸은 지난 칸이라 `available: false`예요. 그래서 "지금·바로·당장" 요청은 이 도구가 아니라 `room_status`(2.3)로 현재 방 상태를 보고 `start_now_reservation`(3.1.1)으로 제안해요 (#62).

### 2.2 `my_reservations` (구현 완료, #5)

**언제:** "내 예약 보여 줘", 취소·퇴실 전에 대상 예약 id 찾기. **입력:** 없음.

**core 응답 (11/2 지영님과 합의)** — 비서가 제안한 모양 그대로예요.
- `accessCode`: 대표자일 때만 6자리, 참여자면 `null`
- `participants[].name`: 가운데를 가린 이름(`홍*동`), 대표자도 포함
- 정렬: 끝나지 않은 예약(`BOOKED`, `IN_USE`)이 위, 그 안에서 시작이 빠른 순. 끝난 예약은 최근 것부터
```json
[ { "id": 7, "room": { "id": 1, "name": "1번 방" },
    "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
    "status": "BOOKED", "owner": true, "accessCode": "482913",
    "participants": [ { "name": "나*준", "owner": true }, { "name": "김*연", "owner": false } ] } ]
```

**도구 출력**
```json
{ "reservations": [ { "id": 7, "roomName": "1번 방",
    "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
    "status": "BOOKED", "owner": true, "participantCount": 2 } ] }
```
- `accessCode`와 참여자 이름은 빼요. 번호는 학생이 웹 화면에서 봐요.
- 끝난 예약은 끝난 지 **14일** 안 것만 줘요(`FINISHED_KEEP_DAYS`, 11/6에 7 → 14: "지난주처럼"이 딱 7일 뒤에도 되게).
- **"지난번처럼 잡아 줘" (11/6):** 도구는 그대로이고 지시문으로 해요. 모델이 이 결과에서 가장 최근에 끝난 예약(`CHECKED_OUT`·`AUTO_CHECKED_OUT`, 없으면 `BOOKED`)의 방·시작·길이를 가져와 같은 요일의 다음 날짜(또는 학생이 말한 날)로 `find_available_rooms{from, to}` → `create_reservation` 제안까지 가요. 끝낸 예약만 있으면 빠른 답장에 "지난번처럼 다시 잡아 줘"가 떠요. 측정 Q16
- `status`: `BOOKED`, `IN_USE`, `CHECKED_OUT`, `AUTO_CHECKED_OUT`, `NO_SHOW`, `CANCELED` (core `V1__init_schema.sql`과 같음)

**오류:** 헤더 없음 → core를 부르지 않고 "로그인이 필요합니다". core 401·403은 core 문장 그대로.

### 2.2.1 `show_access_code` (비서 쪽 구현, #39)
"입실 번호 알려 줘", "문 비밀번호 뭐였지?" → **번호는 모델을 거치지 않아요** (11/3 결정). 모델은 대표자인지와 안내 문장만 받고, 번호는 학생 화면 카드가 REST로 따로 받아요.

**도구 입력:** `reservationId`(선택). 비웠을 때 끝나지 않은(상태가 예약됨·사용 중이고 종료 시각 전) **대표자** 예약으로 답해요. 번호는 대표자만 받고 대표자 예약은 동시에 1건이라(FR-RSV-003) 참여자 예약은 목록에 넣지 않아요. 참여자 예약만 있으면 대표자에게 받으라고 안내해요. 대표자 예약이 여러 건으로 보이면(core 규칙과 다른 응답) 추측하지 않고 `choices`(id·방·시간·대표자 여부, 번호 없음)를 돌려주고, 모델은 목록을 보여 주고 학생이 고른 id로 다시 불러요 (11/3 영준, 11/3 리뷰 반영).

**도구 출력** (`accessCode` 필드 자체가 없음)
```json
{ "reservationId": 7, "owner": true, "cardShown": true,
  "message": "학생 화면에 입실 번호 카드로 보여 줬음. 번호는 이 결과에 없고 모델은 알 수 없음. 번호를 지어내지 말 것. 번호는 시작 10분 전부터 입력할 수 있다고 함께 안내할 것",
  "choices": [] }
```

| 경우 | `owner` | `cardShown` | `message` |
|---|---|---|---|
| 대표자, `BOOKED`·`IN_USE`, 종료 시각 전 | true | true | 카드로 보여 줬음, 10분 전부터 입력 가능 안내 |
| 참여자 (id 없이 물었고 참여자 예약만 있을 때도) | false | false | 번호는 대표자만 받아요. 대표자에게 번호를 받아 주세요. |
| 끝난 예약(퇴실·취소·노쇼, 또는 상태는 그대로인데 종료 시각이 지남) | true | false | 이미 끝났거나 취소된 예약이라 입실 번호를 쓸 수 없어요. |
| id 없음, 대표자 예약 여러 건 (core 규칙과 다른 응답) | null | false | 지금 잡혀 있는 예약이 N개예요. 어느 예약의 입실 번호를 볼까요? (목록을 보여 주고 다시 부르는 지시는 도구 설명에만 둬요) |
| 없는 예약 id | — | — | 도구 오류 `RESERVATION_NOT_FOUND` "찾을 수 없는 예약이에요" |
| id 없음, 잡혀 있는 예약(예약됨·사용 중) 없음 | — | — | 도구 오류 `RESERVATION_NOT_FOUND` "지금 잡혀 있는 예약이 없어요. 예약을 하면 입실 번호가 생겨요." |

**화면 카드 API (REST, 모델은 못 부름):** `GET /api/reservations/{id}/access-code` (mcp-server). 학생 본인 헤더로 core `/me`를 다시 불러 그 예약 한 건만 봐요.
- `200 { reservationId, roomName, startAt, endAt, accessCode, note }`, `Cache-Control: no-store`. `note`는 "시작 10분 전부터 입력할 수 있어요."(FR-ACC-001)
- `403 NOT_RESERVATION_OWNER`(대표자 아님), `409 RESERVATION_FINISHED`(끝난 예약), `404 RESERVATION_NOT_FOUND`, `401 UNAUTHORIZED`(헤더 없음, core 안 부름), `502 ACCESS_CODE_UNAVAILABLE`(대표자인데 core가 번호를 안 줌)
- 번호는 로그·도구 결과·예외 문장에 넣지 않아요. 기록에는 경로·걸린 시간·성공 여부만 남아요.
- core에 예약 한 건 조회 API가 생기면 `/me` 대신 그쪽을 써요 (확인 필요).

### 2.3 `room_status` (구현 완료, #62)

**언제:** "지금 바로 쓸 수 있는 방", "지금 빈 방 있어?", "당장 들어갈 방". 날짜·시간을 말한 질문은 `find_available_rooms`. **입력:** 없음.

**core 요청** `GET /api/rooms/status` (학생 로그인 토큰을 그대로 전달해요. 게이트웨이 비로그인 허용 목록에는 없어요. 실제 게이트웨이·core 연동은 확인 필요)

**도구 출력**
```json
{ "now": "2026-11-03T14:17:00+09:00", "availableCount": 2,
  "rooms": [
    { "roomId": 1, "roomName": "1번 방", "minPeople": 3, "maxPeople": 5, "status": "IN_USE",
      "currentEndAt": "2026-11-03T15:00:00+09:00", "nextStartAt": null, "latestEndAt": null, "presence": "OCCUPIED" },
    { "roomId": 2, "roomName": "2번 방", "minPeople": 3, "maxPeople": 5, "status": "AVAILABLE",
      "currentEndAt": null, "nextStartAt": "2026-11-03T15:00:00+09:00", "latestEndAt": "2026-11-03T15:00:00+09:00", "presence": "EMPTY" }
  ],
  "note": "지금 바로 쓰려면 start_now_reservation으로 제안해요. 입실은 시작 10분 안에 해야 해요." }
```
- `status`: `AVAILABLE`(바로 잡을 수 있음) · `RESERVED`(예약 시간인데 아직 입실 전) · `IN_USE`. core 값 그대로
- `latestEndAt`은 비서가 계산해요(`ShowRoomStatus`): 지금 + 최대 2시간을 30분 칸으로 **올린** 시각(14:17 → 16:30)과 다음 예약 시작을 30분 칸으로 **내린** 시각(14:40 → 14:30) 중 이른 쪽. core `ReservationTime.instant`와 같은 규칙이라 모델이 시간을 세지 않아요. 내린 시각이 지금 이전·같으면 `null`(바로 못 씀)
- `availableCount`는 `latestEndAt`이 있는 방 수. 0이면 `note`가 "지금 바로 쓸 수 있는 방이 없어요…"
- `presence`는 센서 재실(OCCUPIED/EMPTY/UNKNOWN). 비어 있는데 OCCUPIED면 누가 무단으로 쓰는 중일 수 있어요(모델은 그대로 전함)

**오류:** core 오류는 그대로. 2xx인데 본문이 비거나 `rooms`가 없으면 `502 CORE_BAD_RESPONSE` "방 현황을 불러오지 못했어요"(빈 방 없음으로 안내하지 않아요, `usage_rules`와 같은 규칙). 한계: 영준이 화면에서 즉시 시작을 돌리니 "30분으로 나오더라"는 보고가 있는데(11/5), 화면 기본값인지 core 올림 규칙인지 확인 필요

### 2.4 `usage_rules` (비서 쪽 구현, core #57 기준)
- 입력 없음. `GET /api/rules`를 학생 헤더와 함께 불러 응답을 그대로 돌려줘요 (core는 로그인 없이도 열어 둠)
- 응답 `{ reservation: { bookingWindowDays, slotMinutes, maxMinutes, checkinOpenBeforeMinutes, noShowMinutes, instantNoShowMinutes, extension: { maxCount, openBeforeMinutes, maxMinutes, chainGapMinutes } }, conduct: [{ key, title, rule, penalty }], reminders: { checkin, checkout } }` (모양은 docs #37)
- 숫자는 core가 실제 검사에 쓰는 설정값이라 비서가 따로 외워 두지 않아요. 도구 설명에 "결과에 없는 규칙은 지어내지 않는다"를 넣었어요
- 본문이 비었거나 `reservation`이 없으면 `502 CORE_BAD_RESPONSE` "이용 규칙을 불러오지 못했어요"로 안내해요

### 2.5 `my_schedule` (비서 쪽 구현, #63)
"내일 수업 끝나고 빈방", "마지막 수업 30분 전에 잡아 줘", "오늘 수업 뭐 있어?" → 학생이 **직접 넣은** 주간 시간표에서 그날 수업을 돌려줘요. core·학사시스템은 부르지 않아요 ([설계.md](설계.md) 5장).

- 입력: `date` (`YYYY-MM-DD`, 없으면 오늘 서울). 형식이 틀리면 오류 "날짜는 YYYY-MM-DD 형식이어야 해요."
- 출력 (오류 아님):

```json
{ "date": "2026-11-06", "dayOfWeek": "금", "code": null,
  "classes": [ { "name": "운영체제", "startAt": "2026-11-06T09:00:00+09:00", "endAt": "2026-11-06T10:15:00+09:00" },
               { "name": "자료구조", "startAt": "2026-11-06T13:00:00+09:00", "endAt": "2026-11-06T14:50:00+09:00" } ],
  "lastClassEndAt": "2026-11-06T14:50:00+09:00",
  "searchFromAt": "2026-11-06T15:30:00+09:00", "bufferMinutes": 30, "note": null }
```

| 경우 | `code` | `classes` | `lastClassEndAt`·`searchFromAt` | `note` |
|---|---|---|---|---|
| 그날 수업 있음 | `null` | 시작 순 | 마지막 끝, 끝 + 여유를 다음 30분 칸으로 올림 | `null` |
| 시간표는 있는데 그날 수업 없음 | `null` | `[]` | `null` | "이 날은 입력한 시간표에 수업이 없어요." |
| 시간표를 아직 안 넣음 | `NO_SCHEDULE` | `[]` | `null` | "아직 넣은 시간표가 없어요. 화면의 [내 시간표]에서 …" |

- `searchFromAt` = `lastClassEndAt` + `mspace.schedule.buffer-minutes`(30)를 `slot-minutes`(30) 칸으로 **올림**: 14:50 → 15:30, 15:00 → 15:30, 15:01 → 16:00. 모델은 시간을 세지 않고 이 값을 `find_available_rooms`의 `from`에 그대로 넣어요
- 모델에 가는 값은 과목명·시각뿐이에요. 강의실·교수명·학번은 받지도 저장하지도 않아요
- 로그인 헤더가 없거나(401) 저장소(Redis)에 닿지 못하면(`SCHEDULE_UNAVAILABLE`) 오류 결과예요. Redis가 죽었을 때 `NO_SCHEDULE`로 답하지 않아요(없는 척하면 "넣어 주세요"로 잘못 안내)

**시간표 넣기 API (REST, 모델은 못 부름):** 화면 → agent `/api/agent/schedule` → mcp-server `/api/schedule/me`. 둘 다 학생 헤더 그대로, `Cache-Control: no-store`.

| 메서드 | 본문 / 응답 | 오류 |
|---|---|---|
| `PUT` | `{ "classes": [ { "dayOfWeek": "MON", "startTime": "09:00", "endTime": "10:15", "name": "자료구조" } ] }` → 200 `{ classes: [{dayOfWeek, startTime, endTime, name}], updatedAt }` (통째로 바꿈) | 400 `INVALID_REQUEST`(요일 MON~SUN·HH:mm·시작<끝·과목명 1~30자·1~40칸), 400 `SCHEDULE_OVERLAP`(같은 요일 겹침) |
| `GET` | 200 위와 같은 시간표 (요일·시작 순) | 404 `NO_SCHEDULE` |
| `DELETE` | 204 | — |

공통: 401 `UNAUTHORIZED`, 503 `SCHEDULE_UNAVAILABLE`(Redis), agent에서 mcp-server에 닿지 못하면 503 `TOOLS_UNAVAILABLE`.

**시간표 캡처 읽기 API (REST, agent만, 모델은 못 부름):** `POST /api/agent/schedule/parse`, `multipart/form-data`의 `image` 한 장(PNG·JPEG·WebP, 5MB까지). 에브리타임 같은 시간표 캡처를 Gemini가 읽어 **초안**을 돌려줘요. **저장하지 않아요.** 화면이 확인 카드로 보여 주고 학생이 고친 뒤 위 `PUT`으로 넣어요.

| 응답 | 뜻 |
|---|---|
| 200 `{ "classes": [{dayOfWeek, startTime, endTime, name}], "dropped": 1, "note": "읽지 못한 칸이 1개 있어요. 확인하고 고쳐 주세요." }` | `classes`는 `PUT` 본문과 같은 모양. 요일·시각이 틀린 줄(끝≤시작, 25:00 등)·중복·40개 초과는 버리고 `dropped`로 세요. 과목명은 30자까지(`PUT` 검사와 같은 한도). 하나도 못 읽으면 `classes: []` + "직접 입력" 안내(오류 아님) |
| 400 `INVALID_IMAGE` | 사진이 없거나 형식·크기가 안 맞음, 선언은 PNG인데 실제 바이트가 아님(매직 넘버 검사), 5MB 초과 (모두 모델을 부르지 않아요) |
| 401 `UNAUTHORIZED` | 로그인 헤더 없음 |
| 429 `LLM_RATE_LIMITED` · 503 `LLM_UNAVAILABLE` | Gemini 한도·장애 |
| 503 `LLM_NOT_CONFIGURED` | 키가 없거나 그림을 못 읽는 모델(`LLM_PROVIDER=ollama`). 직접 입력 안내 |

개인정보: 그림은 모델 요청에만 실리고 서버에 저장·로그하지 않아요(로그에는 크기·걸린 시간만). 모델 지시문에 "교수 이름·강의실·학번·사람 이름은 적지 않는다"를 넣고, 결과도 과목명·시각만 받아요. 다만 캡처 자체에 이름·학번이 찍혀 있으면 외부 AI(Gemini)로 나가니, **화면에서 그 부분을 잘라 올리도록 안내**해요(설계 5장). 시연은 테스트 계정 캡처만 써요.

**비서 성향 API (REST, agent만, 11/6):** `GET /api/agent/persona` → `{style, label, description, options:[{style,label,description}×3]}`, `PUT /api/agent/persona {style: QUIET|ACTIVE|NAGGING}`(400 `INVALID_PERSONA`, 저장 실패 503 `MEMORY_UNAVAILABLE`). 채팅 "잔소리 모드로 해 줘"도 같은 저장을 모델 없이 해요(`tools: ["persona"]`). 성향은 지시문 끝 한 토막만 바꿔요 (설계 5.v).

**오늘 브리핑 API (REST, agent만, 모델은 못 부름, 11/5 밤):** `GET /api/agent/briefing`. 채팅에 "브리핑"이 들어가면 같은 결과를 모델 없이 답으로 줘요(`tools: ["briefing"]`, 11/6). 학생 헤더로 `my_schedule`(오늘)·`my_reservations`·`room_status`를 **서버가 직접** 부르고(모델 안 거침, 토큰 0) 한 문단으로 묶어요. 화면이 첫 화면·"오늘 브리핑" 카드로 보여 주고, [듣기] 버튼은 `text`를 브라우저 `speechSynthesis`로 읽으면 돼요(#64 TTS의 글 버전).

```json
{ "date": "2026-11-06", "dayOfWeek": "금", "generatedAt": "2026-11-06T08:00:00+09:00",
  "schedule": { "classes": [ { "name": "자료구조", "start": "09:00", "end": "10:15" } ], "lastClassEnd": "14:50", "note": null },
  "freePeriod": { "periodStart": "11:00", "periodEnd": "13:00", "roomName": "4번 방", "start": "11:00", "end": "12:30", "minutes": 90,
                  "suggestion": "11:00 4번 방 1시간 30분 잡아 줘" },
  "afterClass": { "searchFrom": "15:30", "roomName": "2번 방", "start": "15:30", "end": "17:30", "minutes": 120,
                  "suggestion": "15:30 2번 방 2시간 잡아 줘", "note": null },
  "reservations": { "items": [], "note": null },
  "rooms": { "availableNames": ["2번 방", "3번 방"], "earliestLimit": "09:30", "note": null },
  "text": "11월 6일 금요일 브리핑이에요. 오늘 수업은 자료구조 09:00–10:15, 운영체제 13:00–14:50 두 개예요. 마지막 수업은 14:50에 끝나요. 공강 11:00–13:00에는 4번 방을 11:00부터 1시간 30분 쓸 수 있어요. 수업 끝나고 15:30부터 2번 방을 2시간 쓸 수 있어요. 잡아 둔 예약은 없어요. 지금 바로 쓸 수 있는 방은 2번 방, 3번 방 두 개예요.",
  "hints": [], "suggestions": ["15:30 2번 방 2시간 잡아 줘", "11:00 4번 방 1시간 30분 잡아 줘"] }
```

**수업 끝나고 쓸 수 있는 칸 `afterClass`·공강 `freePeriod` (11/6):** 오늘 수업이 있고 대표자로 잡은 예약이 없으면 `find_available_rooms{date=오늘}`을 한 번 더 불러(하루 전체 빈 구간) 두 가지를 골라요. `afterClass`는 searchFromAt부터 가장 이른 칸 하나(가장 이른 시작 → 같은 시작이면 더 긴 길이(최대 2시간) → 방 번호). 수업이 이미 끝났으면 지금(30분 칸 올림)부터 봐요. `suggestions`의 문장은 화면 버튼 글이고, 누르면 채팅에 그대로 보내 모델이 `create_reservation` 확인 카드까지 만들어요(브리핑 → 한 번 누르기 → 확인 → 예약). 안 보는 경우(`afterClass: null`): 시간표 없음, 오늘 수업 없음, 수업 끝+여유가 다음 날로 넘어감, 대표자 예약 있음(동시 1건이라 core가 거절). 칸이 없으면 `note: "수업 끝나고 오늘 쓸 수 있는 방은 없어요."`, 조회 실패면 `note: "수업 뒤 빈방을 확인하지 못했어요."`. `freePeriod`는 수업 사이 **가장 긴 공강**(앞 수업 끝 + 여유 30분을 칸으로 올림 ~ 다음 수업 시작을 칸으로 내림)이 1시간 이상일 때 그 안에서 같은 규칙으로 고른 칸이에요. 공강이 이미 지났거나 짧거나 빈방이 없으면 `null`(note 없음). 공강 중간에 열면 지금 칸부터 남은 만큼만. `suggestions`는 수업 뒤 → 공강 순(최대 2개, 대표자 예약은 1건이라 둘 중 하나만 잡게 돼요).

| 경우 | 응답 |
|---|---|
| 시간표 없음 | `schedule.classes: []`, `hints: ["OPEN_SCHEDULE"]`, 문장에 "아직 넣은 시간표가 없어요. 넣어 두면 …" → 화면은 [내 시간표 넣기] 버튼 |
| 예약 없음 / 빈 방 없음 | `items: []` / `availableNames: []`, 문장 "잡아 둔 예약은 없어요." / "지금 바로 쓸 수 있는 방은 없어요." |
| 오늘 예약은 없고 뒤에 있음 | "다음 예약은 11월 9일(월) 3번 방 10:00–11:00이에요." |
| 도구 하나 실패 | 그 칸만 `null` + `note`("예약을 불러오지 못했어요.") — 나머지는 그대로. 전체 실패로 만들지 않아요 |
| 수업 뒤 칸 | `afterClass` + `suggestions`(위). 요청 하나 = 기본 mcp-server 호출 3번·core 조회 2번(`my_schedule`은 core를 안 부르고 Redis만), 수업 있고 대표자 예약 없을 때만 mcp-server 4번·core 3번(공강 칸도 같은 조회로 고르니 더 늘지 않아요) |
| 401 `UNAUTHORIZED` | 로그인 헤더 없음 |

- 끝난 예약(`CHECKED_OUT`·`CANCELED`·`NO_SHOW` 등)은 빼고 `BOOKED`·`IN_USE`만, 오늘 것 먼저. `rooms.earliestLimit`은 빈 방 중 가장 이른 `latestEndAt`(그 전엔 어느 방이든 됨)
- `Cache-Control: no-store`. 도구를 세 번 부르니 core 조회 3번이에요. 첫 화면에서 매번 부르면 core 부하가 늘어서, 화면은 열 때 1번 + 당겨서 새로 고침으로 제한해요(확인 필요: front)

### 2.6 `week_plan` (비서 쪽 구현, 11/6)
"이번 주에 수업 끝나고 2시간 쓸 수 있는 날", "언제 비어?", "다음 주 중에 스터디 날 잡아 줘" → 오늘부터 7일을 **날마다 `my_schedule` → `find_available_rooms`로 이어 붙여** 하루에 하나씩 "수업 끝난 뒤 가장 이른 칸"을 줘요. 모델이 날짜마다 도구를 번갈아 부르면 14번이라 호출 한도(8번)에 걸려서, 서버가 한 번에 계산해요.

- 입력: `minutes`(30분 단위, 30~240, 없으면 120), `headcount`(선택). 길이가 틀리면 오류 `INVALID_REQUEST` "길이는 30분 단위로 30분부터 240분까지예요."
- 출력 (오류 아님):

```json
{ "from": "2026-11-05", "to": "2026-11-11", "minutes": 120, "code": null,
  "days": [ { "date": "2026-11-05", "dayOfWeek": "목", "classCount": 1, "lastClassEndAt": "2026-11-05T14:50:00+09:00",
              "searchFromAt": "2026-11-05T15:30:00+09:00",
              "option": { "roomId": 1, "roomName": "1번 방", "startAt": "2026-11-05T17:00:00+09:00", "endAt": "2026-11-05T19:00:00+09:00" }, "reason": null },
            { "date": "2026-11-06", "dayOfWeek": "금", "classCount": 0, "lastClassEndAt": null,
              "searchFromAt": "2026-11-06T09:00:00+09:00", "option": null, "reason": "빈 시간 없음" } ],
  "note": null }
```
- 날마다: 수업이 있으면 `searchFromAt`(끝 + 여유를 칸으로 올림)부터, 없으면 `mspace.schedule.plan-from-time`(기본 09:00)부터 봐요. 그 뒤로 `minutes`가 들어가는 가장 이른 시작(같으면 방 번호 순) 하나만 `option`이에요
- 수업 끝 + 여유가 다음 날로 넘어가면(밤늦은 수업) 그날은 `reason: "수업이 늦게 끝나 그날은 안 봄"`
- 인원 때문에 방이 없으면 `reason`에 `find_available_rooms`의 인원 안내가 그대로 들어가요
- 시간표가 없으면 `code: "NO_SCHEDULE"`이지만 오류가 아니라 매일 09:00부터 본 결과를 주고, `note`에 "[내 시간표]를 넣으면 수업 끝난 뒤로 맞춰 드릴게요"
- 쓸 수 있는 날이 하나도 없으면 `note: "이 기간에는 그 길이로 쓸 수 있는 시간이 없어요. 길이를 줄이거나 인원을 바꿔 볼 수 있어요."`
- **부하:** core `GET /api/rooms/availability`를 7번(날 수 `plan-days`) **동시에**(가상 스레드) 불러요. 순서대로 부르면 core 읽기 제한 3초 × 7이 비서 도구 제한 10초를 넘을 수 있어서예요. 하루가 실패하면(core 5xx·시간 초과) 그날만 `reason: "이 날은 예약 시스템 조회에 실패해 확인하지 못했어요"`로 적고 나머지는 돌려줘요. 인증(401·403)과 시간표 저장소 장애(503)는 전체 오류예요. 트래픽이 늘면 하루치 응답을 짧게(30초) 캐시하는 게 다음 수예요. 읽기만 해서 트랜잭션·동시성 문제는 없고, 보여 준 칸을 남이 먼저 잡으면 예약 때 core가 409로 막아요
- 비서 꼬리말: `week_plan`은 시간표와 예약 시스템을 둘 다 본 결과라 "(예약 시스템 HH:MM 조회 · 입력한 시간표 기준)"이 붙어요. `NO_SCHEDULE`이면 시간표 근거는 빼고 화면에 [내 시간표 넣기] 버튼 신호(`hints`)를 줘요

### 2.7 학교 생활 도구 (11차 회의 11/13, 재웅 제안)
아침 브리핑에 날씨·교내 셔틀을 붙이고, 식당 혼잡도는 나중에 붙일 자리만 둬요. 셋 다 예약 코어를 부르지 않는 읽기 도구예요. 로그인한 학생만 쓰게 자격 정보는 확인하지만 값은 어디에도 넘기지 않아요.

| 도구 | 입력 | 출력 | 오류·없음 |
|---|---|---|---|
| `campus_weather` | `date`(선택, 오늘·내일) | `summary`(맑음·흐림·비…), `minTemperature`·`maxTemperature`(℃), `rainChance`(%), `umbrella`(확률 ≥ `umbrella-percent`), 오늘이면 `nowTemperature`·`nowSummary`, `note`("Open-Meteo 예보 기준이에요.") | 모레 이후 `INVALID_REQUEST` "오늘과 내일만", 예보 서버 실패 `WEATHER_UNAVAILABLE`(503), 꺼 둠 `WEATHER_OFF` |

- **날씨:** `GET https://api.open-meteo.com/v1/forecast?latitude=35.1408&longitude=126.93&current=…&daily=…&timezone=Asia/Seoul&forecast_days=2`. 키·비용 없음(비상업 무료). 학생 정보·토큰은 보내지 않아요. 같은 예보를 `cache`(기본 10분) 동안 다시 써서 학생이 많아도 호출이 10분에 1번이에요. 연결 3초 제한, 실패하면 지어내지 않고 오류. 좌표는 조선대 본관 근처 값이라 확인 필요
- **셔틀:** 학교 [교내버스 안내](https://www3.chosun.ac.kr/chosun/160/subview.do)(11/13 읽음)의 본관 순환·사회과학관·글로벌하우스 버스를 `mspace.campus.shuttle.routes`에 넣었어요. 노선마다 정해진 시각(`departures`)과 시간대(`windows`: `from`·`to`·`every`·`note`)를 둘 수 있어요
  - "17:00~18:45 15분 간격"은 17:00부터 15분씩 펼친 시각이에요. 공지가 시작점을 적지 않아 실제와 몇 분 다를 수 있어서 `basis`에 밝혀요
  - "07:40~17:00 수시 운행"처럼 간격이 없는 시간대는 시각을 지어내지 않고 `running`에 시간대 문장만 넣어요
  - 학기 중·방학 중 시간표가 달라 `mspace.campus.shuttle.season`(기본 `SEMESTER`)으로 고르고, 노선의 `season`이 비면 둘 다예요. 방학이 되면 설정 한 줄만 `VACATION`으로 바꿔요
  - 공지에 운행 요일은 없고 "공휴일 운행 안 함"만 있어요. 요일은 기본(월~금)으로 두고 공휴일은 `basis`로만 알려요(공휴일 달력은 아직 없음). 주말 운행은 확인 필요
  - 시내버스(419·57·61·87번, 해오름관 06:00~22:20)는 배차 간격이 공지에 없어 셔틀 도구에 넣지 않고, 실시간 도착은 `city_bus_arrival`로 봐요
- **시내버스(영준 11/13):** 공공데이터포털 [전남광주통합특별시_광주버스정보](https://www.data.go.kr/data/15157923/openapi.do)(무료, 이용 허락 제한 없음). `GET https://apis.data.go.kr/6290000/gj_bis/arriveInfo?serviceKey=…&BUSSTOP_ID=…&resultType=json`
  - **키:** 포털 로그인 → 위 페이지 [활용신청] → 마이페이지의 "일반 인증키(Decoding)"를 서버 `.env`의 `GWANGJU_BUS_KEY`에 넣어요(커밋 금지). 키가 비면 도구는 "아직 연결 전이에요. 광주 버스 앱에서 정류장 번호 1177을 찾아 주세요"로 답해요
  - **정류장 번호:** 1177은 표지판(ARS) 번호이고, API는 다른 체계의 정류소 ID(`BUSSTOP_ID`, 포털 예시 2873)를 받아요. `GWANGJU_BUS_STOP_ID`가 비면 처음 한 번 정류소 정보(`/stationInfo`)에서 `ARS_ID == 1177`인 정류소의 `BUSSTOP_ID`를 찾아 기억해요. 키를 받으면 찾은 ID를 `.env`에 적어 두는 걸 추천해요
  - **확인 필요:** 포털 페이지에 상세 경로·응답 필드가 나오지 않아(작업 환경에서 포털 접속도 막힘) 경로(`arriveInfo`·`stationInfo`)와 필드(`BUSSTOP_LIST`·`LINE_NAME`·`REMAIN_MIN`·`REMAIN_STOP`, `STATION_LIST`·`ARS_ID`·`BUSSTOP_ID`)는 광주 BIS의 기존 응답 모양을 따랐어요. 설정(`arrive-path`·`station-path`)으로 경로를 바꿀 수 있고, 모양이 다르면 지어내지 않고 `BUS_UNAVAILABLE`이에요. 키를 받으면 실제 응답 한 번으로 확인해요
  - 같은 도착 정보를 30초 동안 다시 써서 학생이 많아도 API 호출이 30초에 1번이에요(캐시가 끝난 순간 동시에 물어도 한 요청만 부르고 나머지는 그 값을 써요). 학생 정보는 보내지 않아요
  - 키가 있으면 주소는 https만 받아요(키가 주소 뒤에 붙어 가서). "N건"이라면서 목록이 없거나 항목을 못 읽으면 "오는 버스 없음"이 아니라 `BUS_UNAVAILABLE`이에요
- **비서:** 지시문에 날씨·셔틀·시내버스·식당 규칙 한 줄. 이 도구 결과에는 "(예약 시스템 … 조회 기준)" 꼬리말을 붙이지 않아요(예약 시스템을 본 게 아니라서)
- **오늘 브리핑(`GET /api/agent/briefing`):** 날씨를 맨 앞, 셔틀을 맨 뒤에 한 줄씩 붙여요. 지금 수시 운행 중인 노선이 있으면 그 시간대를, 아니면 가장 가까운 출발을 말해요. 실패하거나 시간표가 없으면 그 줄만 빼요. `mspace.agent.briefing.campus=false`로 끌 수 있어요
- 모델 평가 세트(`scripts/eval`, 가짜 도구 12개)는 그대로 둬요. 기준 점수(v4d 98.5)를 바꾸지 않으려고요. 학교 생활 발화는 다음 판에 한 가지씩 더해 재요

## 3. 쓰기 도구 (두 단계 확인)

다섯 도구 모두 **1단계(확인안)만 모델이 부를 수 있어요.** 실행은 학생이 화면의 [확인] 버튼을 눌렀을 때만 일어나요. 흐름·토큰 규칙은 [설계.md](설계.md) 2장.

### 3.1 `create_reservation` (구현 완료, #11)

**입력 (모델이 채움)**
```json
{ "roomId": 1, "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00", "headcount": 4 }
```
- 참여자 학번은 모델 입력에 **넣지 않아요.** 확인 카드에서 학생이 직접 입력하고, 에이전트가 core로 바로 보내요(학번이 외부 AI로 안 나가게, 설계.md 2.4, A-5 결정).

**도구 출력 (1단계)**
```json
{ "confirmToken": "c_9f2…", "expiresAt": "2026-11-03T13:02:00+09:00",
  "summary": "1번 방, 11월 3일(화) 14:00–16:00, 4명으로 예약할까요?",
  "notes": [] }
```
- 자정을 넘기면 `notes`에 "자정 이후 부분은 예약할 때 확인돼요".
- `needsParticipants` = 확인 화면에서 받을 학번 수(인원 − 1). `notes`에도 "함께 쓰는 N명의 학번은 확인 화면에서 입력해요".

**확인 실행 API (mcp-server, 모델은 못 부름)**
- `POST /api/confirmations/{confirmToken}` + 학생 본인 헤더 + `{ "participantStudentIds": [...] }`
- 성공 `200 { action: "CREATE", reservationId, status, accessCode, replayed, message }`. `accessCode`는 화면 전용이라 에이전트가 모델에 넘길 때 빼요
- 확인 오류: `404 CONFIRMATION_NOT_FOUND`(없음·남의 토큰), `409 CONFIRMATION_USED`(재사용), `410 CONFIRMATION_EXPIRED`(2분 지남), `400 INVALID_REQUEST`(학번 수가 안 맞음, 이때는 토큰을 쓰지 않아 다시 누를 수 있음)
- core 4xx 오류는 core의 상태 코드·`code`·`message`를 그대로. 두 번 다 응답이 없거나, 응답을 읽지 못하거나, core 5xx·2xx 아닌 응답(302 등)이면 `503 RESERVATION_UNKNOWN` "예약이 됐는지 확인하지 못했어요. 내 예약에서 확인해 주세요." (5xx는 저장 뒤에 났을 수 있어 '다시 시도'로 안내하지 않아요) 

**실행 시 core 요청** (`POST /api/reservations`, core PR #24)
```json
{ "roomId": 1, "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
  "participantStudentIds": ["20230002", "20230003", "20230004"] }
```
- `participantStudentIds`는 대표자 본인을 빼고 적어요. 인원 = 목록 + 1.
- 헤더 `Idempotency-Key: <확인 토큰>` (설계.md 2.3)
- 헤더 `X-Created-Via: AGENT` (core #45, NFR-COM-008). core가 `created_via = AGENT`로 저장해 웹·비서 예약 건수를 따로 세요. 통계용 표시라 권한과는 상관없어요
- 응답 `201`(새로 만듦) 또는 `200`(한 확인 요청 안에서 같은 키로 다시 보냈고 처음 요청이 이미 저장된 경우, 본문 같음) `{ id, roomId, startAt, endAt, status: "BOOKED", headcount, accessCode }` → 학생 화면에는 번호를 보여 주고, 모델에는 `accessCode`를 뺀 값만 넘겨요.
- **agent가 화면에 주는 본문 (11/6):** mcp-server 응답 그대로 + 성공이면 `suggestions`(CREATE·CONTINUE `["입실 번호 보여 줘","내 예약 보여 줘"]`, START_NOW `["입실 번호 보여 줘","연장할 수 있어?"]`, CANCEL `["다른 시간 찾아 줘","지금 빈 방 있어?"]`, CHECKOUT `["내 예약 보여 줘","지금 빈 방 있어?"]`). 같은 결과(action·예약 번호·message, 번호 없음)를 미룬 글로 남겨 다음 채팅 앞에 붙여요. 모델이 "예약됐다"를 알아요(설계 4장 "확인 뒤").

**오류별 안내** (core 코드를 보고 고름. 모두 core `message`를 기본으로 써요)

| HTTP | code | 비서가 덧붙이는 다음 행동 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 본문 형식 오류·필수 값 빠짐·빈 학번. 비서 버그이거나 확인 카드 입력 오류 → 다시 입력 |
| 401 | `UNAUTHORIZED` | 사용자 헤더 없음, 또는 학생 인증을 안 한 대표자 → "로그인(학생 인증)이 필요해요" |
| 400 | `RESERVATION_NOT_ON_SLOT` | 정각·30분으로 바꿔 다시 제안 |
| 400 | `RESERVATION_INVALID_LENGTH` | 2시간 안으로 줄여 제안 |
| 400 | `RESERVATION_IN_PAST` / `RESERVATION_OUT_OF_RANGE` | 날짜 다시 묻기 |
| 400 | `HEADCOUNT_OUT_OF_RANGE` | `message`에 숫자가 들어 있어 그대로 전해요("1번 방은 3명 이상 5명 이하입니다 (입력: 2명)") + 인원에 맞는 방 다시 찾기 |
| 400 | `PARTICIPANT_NOT_FOUND` / `PARTICIPANT_DUPLICATE` | 확인 토큰은 이미 쓰였어요(core까지 갔음). 같은 카드로 다시 누르면 `409 CONFIRMATION_USED` → "학번을 확인하고 처음부터 다시 말해 주세요"(새 확인안). 토큰을 되살릴지는 core가 실패한 요청의 멱등 키를 저장하는지 확인한 뒤 정해요(확인 필요). `NOT_FOUND`는 가입 안 한 학번과 학생 인증 안 한 회원 둘 다예요 |
| 404 | `ROOM_NOT_FOUND` | 방 목록 다시 보여 주기 |
| 409 | `RESERVATION_TIME_TAKEN` | 같은 날 다른 빈 구간 제안 (조회와 예약 사이에 누가 먼저 잡은 경우 포함) |
| 409 | `OWNER_HAS_ACTIVE_RESERVATION` | "끝나지 않은 예약이 있어요" + `my_reservations`로 그 예약 안내 (한 확인 요청 안에서 core 응답이 끊겨 같은 멱등 키로 다시 보낼 때는 처음 요청이 저장됐으면 `200`, 저장되지 않았으면 이번에 만들어져 `201`이 와요. 저장되지 않았는데 다른 끝나지 않은 예약이 있으면 재시도도 이 409를 받고, 4xx는 그대로 안내해요. 학생이 같은 카드로 확인을 다시 보내면 토큰이 이미 쓰여 core까지 가지 않고 `409 CONFIRMATION_USED`예요. 이 409는 대개 웹 등에서 이미 잡은 다른 예약이 있을 때라, 받으면 항상 `my_reservations`로 그 예약을 보여 줘요) |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 비서 버그. "다시 말해 주세요" (설계.md 2.3) |
| 409 | `PARTICIPANT_TIME_TAKEN` | 참여자 중 누가 겹치는지는 core가 알려 주지 않음 → 시간 바꾸기 제안 |

### 3.1.1 `start_now_reservation` (구현 완료, #62) — 즉시 시작 (FR-RSV-103)

**언제:** "지금 2번 방 1시간 쓸래", "당장 들어갈게". 먼저 `room_status`로 비어 있는 방과 `latestEndAt`을 봐요. 날짜·나중 시각이면 `create_reservation`.

**입력 (모델이 채움)** — 시작 시각은 없어요. 학생이 [확인]을 누른 시각을 core가 시작으로 잡아요
```json
{ "roomId": 2, "endAt": "2026-11-03T16:30:00+09:00", "headcount": 3 }
```

**1단계 검사 (`ProposeChange.startNow`)** — [확인] 뒤 실패를 줄이려는 것. 최종 판단은 core
- 끝이 정각·30분이 아니면 `400 RESERVATION_NOT_ON_SLOT`
- 끝이 지금 이전이거나, 지금 + 2시간(`mspace.continue.max-minutes`)을 30분 칸으로 올린 시각보다 늦으면 `400 RESERVATION_INVALID_LENGTH` "지금 바로 쓰기는 지금부터 16:30까지 고를 수 있어요."
- 방이 지금 비었는지는 여기서 보지 않아요(확인을 누르는 사이 바뀔 수 있어서). core가 `409`로 알려 주면 그대로 전해요

**도구 출력 (1단계)**
```json
{ "confirmToken": "c_…", "expiresAt": "…", "summary": "2번 방을 지금부터 16:30까지 3명으로 바로 쓸까요?",
  "notes": ["확인을 누른 시각부터 시작돼요. 10분 안에 키패드로 입실하지 않으면 노쇼가 돼요.", "함께 쓰는 2명의 학번은 확인 화면에서 입력해요."],
  "needsParticipants": 2 }
```

**확인 실행** `POST /api/confirmations/{token}` + `{ "participantStudentIds": [...] }` → core `POST /api/reservations/instant` `{ roomId, endAt, participantStudentIds }` + `Idempotency-Key` + `X-Created-Via: AGENT`. 응답 `201/200 { id, roomId, startAt, endAt, status, headcount, accessCode }` → `200 { action: "START_NOW", reservationId, status, accessCode, replayed, message: "지금부터 16:30까지 예약했어요. 10분 안에 입실해 주세요." }`. 오류·재시도 규칙은 3.1과 같아요(응답 없으면 같은 키로 한 번 더, 5xx는 `RESERVATION_UNKNOWN`). 확인을 누른 시각에 저장된 끝 시각이 이미 지났으면(15:59:30에 16:00으로 제안 → 16:00:10에 확인) core를 부르지 않고 `400 RESERVATION_INVALID_LENGTH` "끝 시각이 이미 지났어요". 토큰은 남아 있으니 끝 시각만 다시 골라 제안해요.

**core 409** (ReservationTime.instant·CreateReservationService): `RESERVATION_TIME_TAKEN`(지금 다른 예약이 있거나 다음 예약과 겹침), `OWNER_HAS_ACTIVE_RESERVATION`, `RESERVATION_BUSY`(입실 번호 충돌 재시도 실패, 다시 누르면 됨). 모두 core `message` 그대로.

### 3.2 `cancel_reservation` (비서 쪽 구현, core 대조 필요)
- 확인안을 만들기 전에 `my_reservations`로 미리 걸러요: 내 목록에 없음 → 404, 대표자 아님 → 403, `BOOKED` 아님 또는 `BOOKED`라도 시작 시각이 됐거나 지남 → `409 RESERVATION_NOT_CANCELABLE`(확인 토큰을 만들지 않음). 미리 거른 건 안내용이고, 실행할 때 core가 다시 판단해요
- 입력 `{ "reservationId": 7 }` → 확인안 "1번 방 11월 3일 14:00–16:00 예약을 취소할까요?" (내용은 `my_reservations`로 채움)
- 실행 `POST /api/reservations/{id}/cancel`. 대표자·`BOOKED`·시작 전만 (FR-RSV-007).
- 응답·오류 (core #6에 들어갈 예정, 11/2 지영님 공유. PR이 나오면 다시 대조)

| HTTP | code | 비서 안내 |
|---|---|---|
| 200 | — | `{ "id": 7, "status": "CANCELED" }` → "취소했어요" |
| 403 | `NOT_RESERVATION_OWNER` | "대표자만 할 수 있습니다" (참여자가 취소) |
| 404 | `RESERVATION_NOT_FOUND` | 없거나 내 예약이 아님 → `my_reservations`로 다시 고르기 |
| 409 | `RESERVATION_NOT_CANCELABLE` | 이미 취소됨(두 번째 취소 포함) / 시작 시각 지남 / 사용 중(퇴실 안내) / 이미 끝남. core에 `RESERVATION_ALREADY_STARTED`는 없어요(core `ErrorCode` 확인). core가 이유마다 문장이 달라서 core의 `message`를 그대로 안내해요 (설계.md 2.3) |
| 503 | `STATUS_CHANGE_UNKNOWN` | core에 닿지 못했거나 응답(502/503/504 포함)을 못 읽음, core 5xx, 2xx도 4xx도 아닌 응답(302 등) → "처리됐는지 확인하지 못했어요. 다시 누르기 전에 내 예약에서 먼저 확인해 주세요." 재시도하지 않아요 (퇴실도 같음). core 4xx(403·404·409)는 위 줄처럼 code를 그대로 넘겨요 |

### 3.3 `checkout_reservation` (비서 쪽 구현, core 응답 확인 필요)
- 응답은 취소와 같은 `{ id, status }`로 가정했어요 (확인 필요)
- 입력 `{ "reservationId": 7 }` → 종료 전이면 "조기 퇴실할까요?"를 확인안에 넣어요 (FR-RSV-008)
- 실행 `POST /api/reservations/{id}/checkout`. `IN_USE`·대표자만. `BOOKED`이면 `409`. core가 조건부 UPDATE라 두 번 눌러도 한 번만 처리돼요.

### 3.4 `continue_reservation` (비서 쪽 구현, core #51 기준)
- 입력 `{ "reservationId": 21, "minutes": 60 }`. `minutes`는 30·60·90·120 중 하나 (FR-RSV-105)
- 확인안 전에 비서가 먼저 거르는 것: 대표자인지, `IN_USE`인지, 지금이 "끝나기 10분 전 ~ 끝나기 전"인지, 30분 단위·최대 120분인지. 숫자는 `mspace.continue` 설정값이고 core 규칙과 같게 둬요
- 확인안 note: 한 번만 연장 가능, 입실 번호가 새로 나옴, 다음 시간에 예약이 있으면 연장되지 않고 지금 예약이 그대로 남음
- 실행 `POST /api/reservations/{id}/continue` 본문 `{ "endAt": "<지금 끝 + minutes>" }`, 헤더 `Idempotency-Key`(= 확인 토큰), `X-Created-Via: AGENT`
- 응답 `201` 새 `IN_USE` 예약(새 `accessCode`), 같은 키 재전송은 `200`. 새 입실 번호는 예약 만들기처럼 화면 카드에만 보여 주고 모델에는 보내지 않아요
- 오류: `409 RESERVATION_EXTENSION_NOT_OPEN`·`RESERVATION_EXTENSION_LIMIT`(이미 연장함)·`RESERVATION_NOT_IN_USE`·`RESERVATION_TIME_TAKEN`, `400 RESERVATION_INVALID_LENGTH`는 core 문장 그대로 안내해요
- 응답이 안 오면 같은 키로 한 번만 다시 보내고, 5xx면 `503 CONTINUE_UNKNOWN`("연장됐는지 확인하지 못했어요")으로 내 예약부터 보게 해요
