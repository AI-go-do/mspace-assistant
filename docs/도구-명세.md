# MCP 도구 명세

> 기준: 요구사항 명세 v0.4, mspace-core 코드(`feat/7-room-availability`, PR #24 예약 생성, 11/2 확인). core에 아직 없는 API는 **확인 필요**로 표시해요.
> 도구가 core를 부르는 방식은 모두 같아요: 에이전트가 보낸 사용자 헤더(`Authorization`, 로그인 전까지는 `X-User-Id`)를 그대로 넘겨요. 관리자 토큰은 쓰지 않아요.
> `X-User-Id`는 core를 `MSPACE_DEV_HEADER=true`로 띄웠을 때만 켜져요. 진짜 core에 붙여 볼 때 꼭 켜요.

## 0. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 시각 | 입력·출력 모두 서울 시간 ISO-8601 `+09:00`. core 응답도 서울 시간으로 되돌려서 넘겨요 ([TS-01](트러블슈팅.md)) |
| 모델에 안 보내는 값 | 6자리 입실 번호(`accessCode`), 참여자 이름, 학번, 전화번호, 토큰 |
| 오류 | 도구 오류 결과(`isError: true`)에 core의 `message`를 그대로 담아요. 모델은 이 문장을 학생에게 전해요 |
| core가 꺼짐·3초 넘게 응답 없음 | `CORE_UNAVAILABLE` "예약 서버에 연결하지 못했어요. 잠시 후 다시 시도해 주세요." |
| 쓰기 도구 | 바로 실행하지 않고 확인안 + 확인 토큰을 돌려줘요 ([설계.md](설계.md) 2장) |

## 2. 읽기 도구

### 2.1 `find_available_rooms` (구현 완료, #6)

**언제:** "내일 오후 2시 빈방", "수업 끝나고 2시간 잡을 방" 같은 빈 시간 질문.

**입력**
```json
{ "date": "2026-11-03", "from": "14:00", "to": "16:00", "headcount": 4 }
```
- `date` 필수. `from`·`to`·`headcount`는 고르기용이라 없어도 돼요.

**core 응답** (`GET /api/rooms/availability?date=2026-11-03`)
```json
{ "date": "2026-11-03", "slotMinutes": 30,
  "rooms": [ { "roomId": 1, "roomName": "1번 방", "minPeople": 3, "maxPeople": 5,
               "slots": [ { "startAt": "2026-11-03T00:00:00+09:00", "endAt": "2026-11-03T00:30:00+09:00", "available": false }, "… 48칸" ] } ] }
```

**도구 출력** (48칸을 그대로 주지 않고 **이어진 빈 구간**으로 합쳐요. 방 5개 × 48칸 = 240줄이 모델 토큰을 먹고, 모델이 칸을 잇다가 틀리기 쉬워서예요)
```json
{ "date": "2026-11-03",
  "rooms": [ { "roomId": 1, "roomName": "1번 방", "minPeople": 3, "maxPeople": 5,
               "free": [ { "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T17:30:00+09:00" } ] } ],
  "note": null }
```
- `headcount`가 있으면 `minPeople ≤ headcount ≤ maxPeople`인 방만 남겨요.
- `from`·`to`를 둘 다 주면 그 시간 **전체**가 빈 구간 안에 들어가는 방만 남겨요. 빈 구간 목록은 그 방의 하루 전체를 그대로 줘요(모델이 다른 시간을 제안할 수 있게).
- `from`만 주면 그 시각 뒤에 끝나는 구간만, `to`만 주면 그 시각 전에 시작하는 구간만 남겨요.
- 맞는 방이 없으면 `rooms: []`와 `note: "조건에 맞는 빈방이 없어요. 다른 시간이나 날짜를 찾아볼 수 있어요."`
- `available: false`는 "지난 칸"이거나 "예약된 칸"이에요. 둘을 구분하지 않아요.

**자정 넘김 (11/2 지영님과 합의):** core는 그대로 두고, 비서는 **시작 날짜만 조회**해요.
- 예: 오늘 11/3, "11/9 23:00–11/10 01:00" → `date=2026-11-09`의 23:00·23:30 칸만 확인하고 바로 예약 확인안으로 가요.
- 11/10 칸은 조회 범위(오늘~+6일) 밖이라 `400 ROOM_DATE_OUT_OF_RANGE`예요. 예약 규칙은 **시작 시각만** 7일 안을 보니까 예약 자체는 돼요(core 테스트로 확인).
- 그래서 `note`에 "자정 이후 부분은 예약할 때 확인돼요"를 넣고, 확인안에도 같은 문장을 넣어요. 이미 차 있으면 예약 때 `409 RESERVATION_TIME_TAKEN`이 와요.

**오류**
- `400 ROOM_DATE_OUT_OF_RANGE` "오늘부터 예약 가능한 기간 안의 날짜만 조회할 수 있습니다"
- `400 INVALID_REQUEST` "요청 형식이 올바르지 않습니다" (`date` 형식이 틀리거나 없음. 비서가 날짜를 만들어 보내니 거의 안 나와요)

**아직 안 되는 것:** 즉시 시작(v0.2)은 "지금 14:17이면 14:00 칸은 지난 칸이라 false"예요. core #13에서 "지금 바로 쓸 수 있음" 값을 넣기로 했어요(지영님, 모양이 바뀌면 먼저 공유).

### 2.2 `my_reservations` (구현 완료, #5)

**언제:** "내 예약 보여 줘", 취소·퇴실 전에 대상 예약 id 찾기. **입력:** 없음.

**core 응답 (11/2 지영님과 합의)** — 비서가 제안한 모양 그대로예요.
- `accessCode`: 대표자일 때만 6자리, 참여자면 `null`
- `participants[].name`: 가운데를 가린 이름(`홍*동`), 대표자도 포함
- 정렬: 끝나지 않은 예약(`BOOKED`, `IN_USE`)이 위, 그 안에서 시작이 빠른 순. 끝난 예약은 최근 것부터
```json
[ { "id": 7, "room": { "id": 1, "name": "1번 방" },
    "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
    "status": "BOOKED", "owner": true, "accessCode": "482913",
    "participants": [ { "name": "나*준", "owner": true }, { "name": "김*연", "owner": false } ] } ]
```

**도구 출력**
```json
{ "reservations": [ { "id": 7, "roomName": "1번 방",
    "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
    "status": "BOOKED", "owner": true, "participantCount": 2 } ] }
```
- `accessCode`와 참여자 이름은 빼요. 번호는 학생이 웹 화면에서 봐요.
- `status`: `BOOKED`, `IN_USE`, `CHECKED_OUT`, `AUTO_CHECKED_OUT`, `NO_SHOW`, `CANCELED` (core `V1__init_schema.sql`과 같음)

**오류:** 헤더 없음 → core를 부르지 않고 "로그인이 필요합니다". core 401·403은 core 문장 그대로.

### 2.3 `room_status` (M2, 확인 필요)
"지금 1번 방 비었어?" → 방마다 지금 사용 중인지, 다음 예약 시각. FR-DEV-102(v0.2)의 방 현황 API를 그대로 써요. 경로와 응답은 core에 생기면 맞춰요.

### 2.4 `usage_rules` (확인 필요)
"음식 먹어도 돼?" → `GET /api/rules`의 수칙을 그대로 돌려줘요(FR-WEB-003: 화면과 비서가 같은 내용을 씀). core에 아직 없어요.

## 3. 쓰기 도구 (두 단계 확인)

세 도구 모두 **1단계(확인안)만 모델이 부를 수 있어요.** 실행은 학생이 화면의 [확인] 버튼을 눌렀을 때만 일어나요. 흐름·토큰 규칙은 [설계.md](설계.md) 2장.

### 3.1 `create_reservation`

**입력 (모델이 채움)**
```json
{ "roomId": 1, "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00", "headcount": 4 }
```
- 참여자 학번은 모델 입력에 **넣지 않아요.** 확인 카드에서 학생이 직접 입력하고, 에이전트가 core로 바로 보내요(학번이 외부 AI로 안 나가게, 설계.md 2.4, A-5 결정).

**도구 출력 (1단계)**
```json
{ "confirmToken": "c_9f2…", "expiresAt": "2026-11-03T13:02:00+09:00",
  "summary": "1번 방, 11월 3일(화) 14:00–16:00, 4명으로 예약할까요?",
  "notes": [] }
```
- 자정을 넘기면 `notes`에 "자정 이후 부분은 예약할 때 확인돼요".

**실행 시 core 요청** (`POST /api/reservations`, core PR #24)
```json
{ "roomId": 1, "startAt": "2026-11-03T14:00:00+09:00", "endAt": "2026-11-03T16:00:00+09:00",
  "participantStudentIds": ["20230002", "20230003", "20230004"] }
```
- `participantStudentIds`는 대표자 본인을 빼고 적어요. 인원 = 목록 + 1.
- 헤더 `Idempotency-Key: <확인 토큰>` (설계.md 2.3)
- 응답 `201`(새로 만듦) 또는 `200`(같은 키 재전송, 본문 같음) `{ id, roomId, startAt, endAt, status: "BOOKED", headcount, accessCode }` → 학생 화면에는 번호를 보여 주고, 모델에는 `accessCode`를 뺀 값만 넘겨요.

**오류별 안내** (core 코드를 보고 고름. 모두 core `message`를 기본으로 써요)

| HTTP | code | 비서가 덧붙이는 다음 행동 |
|---|---|---|
| 400 | `INVALID_REQUEST` | 본문 형식 오류·필수 값 빠짐·빈 학번. 비서 버그이거나 확인 카드 입력 오류 → 다시 입력 |
| 401 | `UNAUTHORIZED` | 사용자 헤더 없음, 또는 학생 인증을 안 한 대표자 → "로그인(학생 인증)이 필요해요" |
| 400 | `RESERVATION_NOT_ON_SLOT` | 정각·30분으로 바꿔 다시 제안 |
| 400 | `RESERVATION_INVALID_LENGTH` | 2시간 안으로 줄여 제안 |
| 400 | `RESERVATION_IN_PAST` / `RESERVATION_OUT_OF_RANGE` | 날짜 다시 묻기 |
| 400 | `HEADCOUNT_OUT_OF_RANGE` | `message`에 숫자가 들어 있어 그대로 전해요("1번 방은 3명 이상 5명 이하입니다 (입력: 2명)") + 인원에 맞는 방 다시 찾기 |
| 400 | `PARTICIPANT_NOT_FOUND` / `PARTICIPANT_DUPLICATE` | 확인 카드에서 학번 다시 입력. `NOT_FOUND`는 가입 안 한 학번과 학생 인증 안 한 회원 둘 다예요 |
| 404 | `ROOM_NOT_FOUND` | 방 목록 다시 보여 주기 |
| 409 | `RESERVATION_TIME_TAKEN` | 같은 날 다른 빈 구간 제안 (조회와 예약 사이에 누가 먼저 잡은 경우 포함) |
| 409 | `OWNER_HAS_ACTIVE_RESERVATION` | "끝나지 않은 예약이 있어요" + `my_reservations`로 그 예약 안내 (같은 확인 재전송은 멱등 키로 `200`이 와서 여기로 안 와요. 키 없이 보낸 경우의 대비로만 `my_reservations`를 확인해요) |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 비서 버그. "다시 말해 주세요" (설계.md 2.3) |
| 409 | `PARTICIPANT_TIME_TAKEN` | 참여자 중 누가 겹치는지는 core가 알려 주지 않음 → 시간 바꾸기 제안 |

### 3.2 `cancel_reservation`
- 입력 `{ "reservationId": 7 }` → 확인안 "1번 방 11월 3일 14:00–16:00 예약을 취소할까요?" (내용은 `my_reservations`로 채움)
- 실행 `POST /api/reservations/{id}/cancel`. 대표자·`BOOKED`·시작 전만 (FR-RSV-007).
- 응답·오류 (core #6에 들어갈 예정, 11/2 지영님 공유. PR이 나오면 다시 대조)

| HTTP | code | 비서 안내 |
|---|---|---|
| 200 | — | `{ "id": 7, "status": "CANCELED" }` → "취소했어요" |
| 403 | `NOT_RESERVATION_OWNER` | "대표자만 할 수 있습니다" (참여자가 취소) |
| 404 | `RESERVATION_NOT_FOUND` | 없거나 내 예약이 아님 → `my_reservations`로 다시 고르기 |
| 409 | `RESERVATION_ALREADY_STARTED` | "시작한 예약은 취소할 수 없습니다" → 사용 중이면 퇴실 안내 |
| 409 | `RESERVATION_NOT_CANCELABLE` | 이미 끝났거나 취소됨(두 번째 취소 포함) → "이미 처리됐어요" |

### 3.3 `checkout_reservation`
- 입력 `{ "reservationId": 7 }` → 종료 전이면 "조기 퇴실할까요?"를 확인안에 넣어요 (FR-RSV-008)
- 실행 `POST /api/reservations/{id}/checkout`. `IN_USE`·대표자만. `BOOKED`이면 `409`. core가 조건부 UPDATE라 두 번 눌러도 한 번만 처리돼요.
